# Dette qualité au fil de l'eau des fichiers modifiés

La dette au fil de l'eau du contrôle qualité hebdomadaire (écarts de style, mutants survivants) n'est jamais traitée en elle-même : elle se corrige quand un chantier modifie de toute façon le fichier concerné, dans la Pull Request de ce chantier ([Contrôle qualité hebdomadaire](controle-qualite-hebdomadaire.md#traitement-des-entrées), au fil de l'eau). Aucun traitement du harnais ne la résorbe : seuls les chantiers le font. La règle vaut donc pour **toute** session qui modifie un fichier du dépôt, dans un lot de chantiers en parallèle ou hors lot, Pull Request d'un harnais comprise (exigence de l'utilisateur, #680).

**Quel que soit l'environnement** (exigence de l'utilisateur) : le harnais fonctionne de même quel que soit l'environnement où une session de travail est lancée, dans le cloud ou sur le poste. Il ne repose donc sur aucun outil de la session : son contrôle et le retrait du ticket de suivi sont faits par le CI (`.github/workflows/quality-debt.yml`), qui s'exécute à l'identique pour toute Pull Request.

- **Ce qui est traité** : chaque entrée de la section « Au fil de l'eau » du ticket de suivi du harnais qualité (étiquettes `quality-audit` et `harness`, [Issues](../revue-tickets/issues.md#tickets-de-suivi-des-harnais)) qui porte sur un fichier que la Pull Request modifie, ajoute, supprime ou déplace (à son ancien chemin, où le contrôle l'a relevée, comme au nouveau), quelle que soit la part du fichier que modifie le chantier. Aucun fichier n'est modifié pour la seule raison d'une entrée : un fichier que le chantier ne touche pas garde sa dette, pour un chantier suivant. Les entrées critiques et prioritaires restent au traitement du contrôle ([Traitement du contrôle qualité à la reprise du travail](traitement-du-controle-qualite-a-la-reprise-du-travail.md)).
- **Quand** : dès que la session sait quels fichiers son chantier modifie, elle lit la section « Au fil de l'eau » du ticket de suivi, avant d'écrire le code, puisque la correction en fait partie (un test qui manque se prévoit avec les autres). Le check de la Pull Request le confirme à chaque push, brouillon compris, un fichier modifié en cours de route apportant ses entrées.
- **Traitement** : chaque entrée est traitée comme au traitement du contrôle ([Contrôle qualité hebdomadaire](controle-qualite-hebdomadaire.md#traitement-des-entrées), lu en entier dès qu'une entrée porte sur un fichier du chantier) : à corriger ou non pertinente, réécriture examinée avant tout rejet, rejet porté dans le code par le mécanisme de l'outil, report seulement si la Pull Request ne peut vraiment pas la corriger, par un ticket qui porte la correction.
- **Dit dans la description** : la description de la Pull Request porte, entre les marqueurs `<!-- quality-debt -->` et `<!-- end-quality-debt -->`, une ligne par entrée traitée, l'entrée telle que le ticket de suivi la porte, précédée de son traitement : `fixed`, `rejected` ou `deferred #<ticket>`. Ce relevé, en anglais comme tout contenu technique ([Qualité du code](../gouvernance/qualite-du-code.md), langue des fichiers techniques), est aussi celui que lit le retrait à la fusion.
- **Check requis** : le job `Quality debt along the way` du workflow échoue tant qu'une entrée au fil de l'eau d'un fichier modifié n'a pas sa ligne dans la description, et donne les lignes à ajouter. Il s'exécute à chaque push et à chaque modification de la description, si bien qu'une ligne ajoutée le fait réussir sans nouveau commit, donc sans revue Codex de plus ([Budget IA](../gouvernance/budget-ia.md)). Il échoue aussi s'il ne peut pas lire le ticket de suivi ou la Pull Request, plutôt que de laisser croire qu'il n'y a pas de dette. Check requis du Ruleset ([Configuration du repository GitHub](configuration-du-repository-github.md)), il empêche la fusion d'une Pull Request qui ignore la dette de ses fichiers.
- **Retrait du ticket** : le traitement d'une entrée est acquis à la fusion de la Pull Request ([Issues](../revue-tickets/issues.md#tickets-de-suivi-des-harnais), point traité aussitôt retiré). Sur le push de `main` qui la fusionne, le job `Remove the handled quality debt` retire du ticket de suivi les entrées que sa description dit `fixed` ou `rejected`, et elles seules, la description du ticket étant relue juste avant d'être réécrite. Une entrée reportée reste dans le ticket jusqu'à la Pull Request qui la corrige.
  - **Retraits l'un après l'autre** : GitHub ne réécrit la description d'un ticket qu'en entier, sans mise à jour conditionnelle qui refuserait une écriture faite sur une lecture périmée (documentation de l'API REST de GitHub, *Use conditional requests* : pas de requête conditionnelle pour une méthode qui écrit). Deux retraits faits en même temps se recouvriraient, le dernier écrit rétablissant les entrées que l'autre venait de retirer. Les retraits partagent donc un groupe de concurrence qui garde en file toutes les exécutions en attente (`queue: max`, documentation GitHub, *Control the concurrency of workflows and jobs*) : ils s'exécutent l'un après l'autre, aucun n'étant annulé.
    - **Alternative écartée (groupe de concurrence à la file par défaut)** : GitHub n'y garde en attente qu'une exécution, et annule celle qui attendait quand une autre arrive (même documentation) : un retrait serait perdu.
  - **Réécriture du contrôle hebdomadaire** : un retrait et la réécriture de la description par le contrôle peuvent encore se recouvrir, une fois par semaine au plus, sans effet durable : le contrôle suivant réécrit la description d'après ce qu'il relève encore, et une entrée corrigée n'y revient pas.
    - **Alternative écartée (même groupe de concurrence que le contrôle)** : le groupe du contrôle, à la file par défaut, annulerait une de ses exécutions en attente au profit d'un retrait, pour un recouvrement sans effet durable.
- **Alternative écartée (scripts lancés par la session, sur le poste)** : ils supposent PowerShell et un `gh` authentifié dans l'environnement de la session, ce que rien ne garantit d'une session lancée dans le cloud, et ne vérifient rien si la session ne les lance pas.
- **Alternative écartée (règle laissée au seul [Contrôle qualité hebdomadaire](controle-qualite-hebdomadaire.md))** : ce concept n'est lu que lorsque le traitement est dû, par la session des harnais dans un lot ; une session de chantier n'avait aucune raison de le lire, ni de consulter le ticket de suivi (constaté, #680, Pull Request #678).
- **Alternative écartée (check qui vérifie la correction elle-même)** : seul le contrôle hebdomadaire sait si un mutant survit encore, par des tests de mutation dont il réserve le coût à une exécution par semaine ([Contrôle qualité hebdomadaire](controle-qualite-hebdomadaire.md#rien-ne-bloque)) ; le check vérifie que chaque entrée a été traitée, et la revue, la manière.
