# Dette qualité au fil de l'eau des fichiers modifiés

La dette au fil de l'eau du contrôle qualité hebdomadaire (écarts de style, mutants survivants) n'est jamais traitée en elle-même : elle se corrige quand un chantier modifie de toute façon le fichier concerné, dans la Pull Request de ce chantier ([Contrôle qualité hebdomadaire](controle-qualite-hebdomadaire.md#traitement-des-entrées), au fil de l'eau). Aucun traitement du harnais ne la résorbe : seuls les chantiers le font, et seulement s'ils savent qu'elle existe. La règle vaut donc pour **toute** session qui modifie un fichier du dépôt, dans un lot de chantiers en parallèle ou hors lot, Pull Request d'un harnais comprise (exigence de l'utilisateur, #680).

- **Ce qui est corrigé** : chaque entrée de la section « Au fil de l'eau » du ticket de suivi du harnais qualité (étiquettes `quality-audit` et `harness`, [Issues](../revue-tickets/issues.md#tickets-de-suivi-des-harnais)) qui porte sur un fichier que la branche modifie, ajoute, déplace ou supprime, quelle que soit la part du fichier que modifie le chantier. Aucun fichier n'est modifié pour la seule raison d'une entrée : un fichier que le chantier ne touche pas garde sa dette, pour un chantier suivant. Les entrées critiques et prioritaires restent au traitement du contrôle ([Traitement du contrôle qualité à la reprise du travail](traitement-du-controle-qualite-a-la-reprise-du-travail.md)).
- **Quand** : dès que la session sait quels fichiers son chantier modifie, avant d'en écrire le code, puisque la correction en fait partie (un test qui manque se prévoit avec les autres) ; puis avant chaque push, la liste étant relue, car un fichier modifié en cours de route apporte ses entrées. Elles sont corrigées avant que la Pull Request passe en « prête pour la revue », pour qu'aucun push ne soit ensuite nécessaire pour elles ([Budget IA](../gouvernance/budget-ia.md)).
- **Liste** : `scripts/Get-QualityDebt.ps1` lit le ticket de suivi et liste, sous chaque fichier modifié de la branche, les entrées au fil de l'eau qui le désignent, en entier ; il dit explicitement qu'il n'y en a aucune, et échoue plutôt que de rien lister s'il ne peut pas lire le ticket.
- **Traitement** : chaque entrée listée est traitée comme au traitement du contrôle ([Contrôle qualité hebdomadaire](controle-qualite-hebdomadaire.md#traitement-des-entrées), lu en entier dès que le script liste une entrée) : à corriger ou non pertinente, réécriture examinée avant tout rejet, rejet porté dans le code par le mécanisme de l'outil, report seulement si la Pull Request ne peut vraiment pas la corriger. La description de la Pull Request dit les entrées corrigées, rejetées ou reportées.
- **Retrait du ticket** : le traitement d'une entrée est acquis à la fusion de la Pull Request ([Issues](../revue-tickets/issues.md#tickets-de-suivi-des-harnais), point traité aussitôt retiré). Avec le reste de la clôture ([Suivi par tickets](../revue-tickets/suivi-par-tickets.md)), la session retire alors du ticket de suivi les entrées corrigées ou rejetées, par `scripts/Remove-QualityDebt.ps1`, qui relit la description juste avant de la réécrire et n'en retire que les lignes nommées : deux sessions qui retirent chacune les leurs ne s'effacent pas l'une l'autre. Une entrée reportée reste dans le ticket jusqu'à la Pull Request qui la corrige.
  - **Alternative écartée (règle laissée au seul [Contrôle qualité hebdomadaire](controle-qualite-hebdomadaire.md))** : ce concept n'est lu que lorsque le traitement est dû, par la session des harnais dans un lot ; une session de chantier n'avait aucune raison de le lire, ni de consulter le ticket de suivi (constaté, #680, Pull Request #678).
  - **Alternative écartée (règle portée par le seul moment « Pousser sur une Pull Request » de la table des moments d'`AGENTS.md`)** : au push, le code du chantier est écrit, alors que la correction d'une entrée, souvent un test, se prévoit avec lui ; la table rappelle en revanche ce concept à ce moment.
  - **Alternative écartée (contrôle dans le CI)** : seul le contrôle hebdomadaire sait si un mutant survit encore, par des tests de mutation dont il réserve le coût à une exécution par semaine ([Contrôle qualité hebdomadaire](controle-qualite-hebdomadaire.md#rien-ne-bloque)).
