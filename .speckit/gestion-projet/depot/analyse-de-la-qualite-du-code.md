# Analyse de la qualité du code

- **SonarQube Cloud** (organisation `tetram76`, projet `Tetram76_bdtheque-claude`, gratuit pour un dépôt public) analyse le code et sa couverture par les tests, sur chaque Pull Request et sur `main`. Ses indicateurs (porte de qualité, couverture, fiabilité, sécurité, maintenabilité…) sont affichés en tête du `README.md`, et il commente chaque Pull Request de son analyse.
- **Analyse de chaque push, indépendante de la non-régression** : elle porte sur la couverture des tests du push, sans qu'ils soient exécutés une seconde fois ([Intégration continue (CI)](integration-continue-ci.md)), et une analyse qui ne peut pas aboutir ne fait jamais échouer le contrôle de non-régression (mise en œuvre : [Outillage de développement .NET](../../choix-implementation/outillage.md), CI).
- **Porte de qualité, condition de fusion** ([Règle de merge](../revue-tickets/regle-de-merge-non-regression-porte-de-qualite-et-revue-codex-obligatoires.md)) : imposée par le Ruleset, qui requiert le check `SonarCloud Code Analysis` de l'application SonarQube Cloud ([Configuration du repository GitHub](configuration-du-repository-github.md)), et non le job du workflow : ce check reflète le verdict de la porte, et n'existe que si l'analyse a abouti. Une analyse qui n'aboutit pas, faute de service ou de jeton, bloque donc la fusion.
- **Code global** : la porte ne juge que le nouveau code ; les problèmes déjà présents sur `main`, ses points sensibles de sécurité non revus et ses notes autres que A sont relevés chaque semaine par le [Contrôle qualité hebdomadaire](controle-qualite-hebdomadaire.md).
- **Retours** : ceux de SonarQube Cloud sont ceux d'un outil d'analyse statique, traités dans le cycle de chaque Pull Request selon [Analyse SonarQube Cloud](../revue-tickets/analyse-sonarqube-cloud.md).
- **Jetons** : l'analyse s'authentifie auprès de SonarQube Cloud avec le secret de dépôt GitHub `SONAR_TOKEN` ; l'agent, pour le marquage des problèmes et le paramétrage du projet, avec un jeton distinct, placé dans la variable d'environnement `SONAR_TOKEN` du poste ([Repository](repository.md)), pour que chacun se révoque sans toucher à l'autre. Une Pull Request venant d'un **fork** n'y a pas accès : son analyse échoue et elle ne peut pas être fusionnée en l'état, comme pour l'analyse des vulnérabilités des images ([Intégration continue (CI)](integration-continue-ci.md)). L'analyse automatique de SonarQube Cloud est désactivée sur le projet : elle exclut l'analyse par le CI, et ne mesure pas la couverture.
- **Périmètre** : le code de la solution, celui de `tests/` comme code de test ; les maquettes de `.speckit/`, les prototypes de `poc/` et les migrations générées par EF Core en sont exclus. Les scripts PowerShell de l'outillage (ex. `scripts/Get-DependencyUpdates.ps1`) et les scripts JavaScript du frontend (`src/Bdtheque.Frontend/wwwroot`, ex. `browser-time-zone.js`) sont analysés, mais exclus de la couverture, que seuls les tests .NET mesurent : ils y compteraient toujours comme non couverts. Exclure un script du frontend de cette mesure ne le dispense pas de tests : chacun de ses comportements est fixé par les tests de bout en bout, qui l'exécutent dans le navigateur ([Outillage de développement .NET](../../choix-implementation/outillage.md), tests). La couverture, que seule cette analyse mesure, suit [Outillage de développement .NET](../../choix-implementation/outillage.md).
- **Nouveau code** : celui qui a changé depuis la dernière version publiée ([Versions et releases](versions-et-releases.md)) : le projet est réglé sur la version précédente (*Previous version*), et chaque analyse porte le tag de la dernière version publiée ; la publication d'une version relance l'analyse de `main` pour que la période commence au commit publié ([Versions et releases](versions-et-releases.md)). Sur une Pull Request, le nouveau code est celui de la PR.
