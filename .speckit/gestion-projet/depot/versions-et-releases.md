# Versions et releases

Les versions de l'application sont connues du dépôt avant leur publication : chaque version à venir est un **jalon** GitHub (*milestone*), auquel sont rattachés les tickets et les Pull Requests qu'elle livre ; chaque version publiée est un **tag** et une **release** GitHub. Une version correspond à un état stable et identifiable de l'application, sur `main`.

- **Numérotation** : [Semantic Versioning](https://semver.org/) (`MAJEUR.MINEUR.CORRECTIF`), tag `v<version>` (ex. `v0.1.0`) :
  - `0.0.x` : les phases qui ne livrent pas encore d'application utilisable, une version par phase (phases 0 à 2) ;
  - `0.1.0` : la première application utilisable (Phase 3, partie 1), puis une version **mineure** par phase ou partie de phase ;
  - `1.0.0` : la version de la première mise en production (déploiement consigné dans [`journal-evenements.md`](../../journal-evenements.md)) ; les versions suivantes gardent une version mineure par phase ou partie de phase ;
  - une version **corrective** (ex. `v0.1.1`) livre une correction publiée entre deux de ces versions.

  Une **version candidate** (RC), testée sur le déploiement interne avant la publication de la version ([Hébergement](../../contraintes-techniques/architecture-deploiement/hebergement.md)), n'a pas de numéro propre : elle est désignée par les images d'une publication à la demande, sous leur tag immuable `sha-<commit>` ([Publication des images Docker](../../choix-implementation/deploiement/publication-des-images-docker.md)). Une **version de développement** (alpha ou bêta), appelée à devenir la version candidate suivante, est désignée de même, et déployée en interne à côté de la production et de la version candidate ([Plusieurs versions sur le NAS](../../choix-implementation/deploiement/plusieurs-versions-sur-le-nas.md)).
  - **Alternative écartée (numéro de pré-version, ex. `v0.1.0-rc.1`, avec son tag et sa release)** : un nom plus lisible que `sha-<commit>`, pour un coût réel : chaque version publiée fait repartir la période du nouveau code de SonarQube Cloud ([Analyse de la qualité du code](analyse-de-la-qualite-du-code.md)), qu'une version candidate amputerait du code ajouté depuis la version précédente, et jalons, tags et releases devraient distinguer les versions candidates des versions publiées.

  La version que livre chaque phase, ou partie de phase, est indiquée dans [`suivi-implementation/`](../../suivi-implementation/index.md).
- **Jalon** : chaque version à venir est un jalon de même nom (`v0.1.0`), dont la description désigne la phase ou la partie qu'elle livre. Il est créé au découpage de cette phase ou de cette partie, avec ses tickets, ou avec le ticket d'une version corrective. Il ne porte pas d'échéance : le projet ne planifie pas de dates.
- **Rattachement** : chaque ticket est rattaché au jalon de la version qui le livre ([Suivi par tickets](../revue-tickets/suivi-par-tickets.md)) ; un ticket hors plan l'est dès que sa réalisation est prévue dans une version, et reste sans jalon tant qu'elle ne l'est pas (ex. une montée de version majeure encore lointaine, un ticket de suivi d'un harnais (étiquette `harness`), que ne réalise aucune PR). Chaque Pull Request fusionnée sur `main` est rattachée au jalon de son ticket de référence, ou, pour un chantier de tickets reliés ([Chantiers en parallèle](../gouvernance/chantiers-en-parallele.md#choix-des-chantiers)), à celui de la version en cours, que complète le lot ; sans ticket, à celui de la version en cours, la première version non publiée. Un ticket fermé sans être réalisé (*not planned*) quitte son jalon.
  - **Documentation technique hors jalon** : un ticket ou une Pull Request qui ne porte que sur la documentation technique ([Documentation technique](../gouvernance/documentation-technique.md), pages de `docs/tech/`) n'a pas de jalon. Elle ne livre rien de l'application ; elle suit chaque version par les Pull Requests qui changent le code et la mettent à jour en même temps que lui, et qui gardent, elles, le jalon de leur ticket (exigence de l'utilisateur).
- **Version publiable** : une version est **publiable** quand tous les tickets de son jalon sont fermés. L'agent signale alors à l'utilisateur que la version est publiable, et n'engage aucune étape de sa publication tant que l'utilisateur ne l'a pas demandée.
- **Publication, sur la seule décision de l'utilisateur** (exigence de l'utilisateur) : une version n'est publiée que lorsque l'utilisateur le décide ; qu'elle soit publiable ne suffit pas, mais reste une condition de sa publication : une version qui n'est pas publiable n'est pas publiée, et l'agent signale à l'utilisateur les tickets de son jalon encore ouverts. La publier quand même demande de redéfinir d'abord le contenu de son jalon, en reportant ses tickets ouverts à une autre version, ce que l'utilisateur décide (exigence de l'utilisateur). Ce n'est pas un acte de gestion que l'agent accomplit de lui-même ([Prise de décision](../gouvernance/prise-de-decision.md)). Une fois la publication demandée, l'agent en mène toutes les étapes, dans cet ordre, chacune ne commençant qu'une fois la précédente réussie (procédure : `README.dev.md`, publication d'une version) :
  - **tag** annoté et signé (clé GPG de [Signature des commits](signature-des-commits.md)), posé sur le commit de `main` qui la complète, ou, pour une version corrective d'une version que `main` a déjà dépassée, sur celui de sa branche de release ([Stratégie de branches](strategie-de-branches.md)) ;
  - **release** GitHub sur ce tag. Une version `0.0.x`, qui ne livre pas d'application utilisable, est marquée **pré-release**. Une version `0.x` à partir de `0.1.0` ne l'est pas, mais **reste une version 0**, de développement initial (exigence de l'utilisateur). Les notes de la release se composent ainsi, dans cet ordre, et sont vérifiées avant publication comme tout texte publié ([Budget IA](../gouvernance/budget-ia.md), mention de Codex) :
    1. **présentation** : un court paragraphe qui présente la version (nouveautés, changements…) avant tout détail, une sorte de *TL;DR* : l'essentiel de la version, lu d'un coup d'œil (exigence de l'utilisateur). Pour une version 0, il l'annonce clairement comme telle, en disant qu'elle n'est pas destinée à la production, réservée à la `1.0.0`, quand viendra la première version livrable tant qu'elle n'est pas atteinte ([Phase 3 — Frontend Blazor](../../suivi-implementation/phase-3-frontend-blazor.md)), et que rien n'est garanti d'une version à l'autre jusque-là (exigence de l'utilisateur). Une rupture de compatibilité y est annoncée ;
    2. **rupture de compatibilité**, s'il y en a une : mentionnée clairement et bien en vue (exigence de l'utilisateur), aussitôt après la présentation et avant tout le reste, dans un encadré d'avertissement de GitHub (`> [!WARNING]`) qui dit ce qui est rompu et ce qu'il faut faire ;
    3. **compatibilité et montée de version** (exigence de l'utilisateur) : la compatibilité de la version avec les précédentes, qui porte autant sur le **fonctionnel** (fonction retirée ou dont le comportement change, données présentées ou reprises autrement…) que sur l'**hébergement** (exigences envers le NAS, Docker ou le reverse proxy…) et le **déploiement** (réglages à ajouter, renommer ou retirer, dossiers à créer, étapes de la procédure qui changent, retour en arrière impossible une fois la base migrée…) (exigence de l'utilisateur) : ce qui change, sur chacun de ces plans, pour qui l'utilise à la place d'une version précédente, établi par l'agent sur ce qui a changé depuis le tag de la version précédente, et les étapes de la montée. Elle dit en particulier depuis quelles versions précédentes la montée se fait directement, et celles qui doivent d'abord passer par une version intermédiaire, que les notes nomment. La première version qui a des images le dit, faute de version précédente ;
    4. **détail** : la liste des changements, rédigée par l'agent à partir des commits qui séparent le tag de la version précédente du commit publié, chaque Pull Request fusionnée y laissant le sien. Les changements y sont regroupés par nature (fonctionnalités, corrections, documentation et spécification, outillage et CI…), et ceux qui vont ensemble sont réunis en un seul point, sans citer ni ticket ni Pull Request (exigences de l'utilisateur). Ainsi, quand une Pull Request ajuste un point d'une Pull Request précédente de la même version, leurs descriptions sont fusionnées en une seule (exigence de l'utilisateur). Comme toutes les notes, la liste se concentre sur ce que l'utilisateur final, celui qui déploie l'application, peut voir : l'application elle-même, son hébergement et son déploiement ; le fonctionnement interne, qui ne l'intéresse pas (spécification, gouvernance, outillage, CI, tests, refactorisations, documentation technique…), n'y figure pas (exigence de l'utilisateur).
       - **Alternative écartée (notes générées par GitHub)** : une ligne par Pull Request, sous une forme imposée (titre, auteur, lien complet), que la configuration de GitHub (`.github/release.yml`) ne permet que de répartir en catégories, d'après les étiquettes ; illisible pour une version de plusieurs centaines de Pull Requests ;
    5. **historique** : un utilisateur pouvant sauter plusieurs versions, les notes des releases précédentes, de la plus récente à la plus ancienne (exigence de l'utilisateur). À partir de la version `1.0.0`, les notes d'une release ne mentionnent plus les versions 0, ni dans l'historique ni ailleurs (exigence de l'utilisateur).

    La release d'une version qui a des images propose en téléchargement un **paquet de déploiement**, léger, pour aider à son déploiement (exigence de l'utilisateur) : une archive `bdtheque-<version>.zip`, sans les sources, qui contient le `docker-compose.yml` de la version, ses images désignées sur `ghcr.io` à son numéro, le `.env.example` des réglages à renseigner et la procédure d'installation, dont les liens mènent aux sources de la version, à son tag, et les notes de sa release, telles que publiées (décisions de l'utilisateur) ;
  - **analyse SonarQube Cloud** de `main`, relancée dès le tag posé : la période du nouveau code commence à la première analyse qui porte la version ([Analyse de la qualité du code](analyse-de-la-qualite-du-code.md)), qui doit être celle du commit publié, et non celle de la fusion suivante, dont les changements en seraient exclus ;
  - **images Docker** de la version, publiées à la demande depuis son tag, sur Docker Hub et sur `ghcr.io` ([Déploiement](../../contraintes-techniques/architecture-deploiement/deploiement.md), [Publication des images Docker](../../choix-implementation/deploiement/publication-des-images-docker.md)), publication qui joint aussi le paquet de déploiement à sa release ; les versions `0.0.x` n'en ont pas, faute d'interface ;
  - **fermeture du jalon**.
- **Déploiement** : le déploiement de la version reste à l'utilisateur.
