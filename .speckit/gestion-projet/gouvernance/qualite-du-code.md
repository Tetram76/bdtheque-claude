# Qualité du code

- La **qualité du code est une préoccupation majeure** et permanente.
- **Exigence de rigueur** : un code qui fonctionne ne suffit pas. L'agent tient tout ce qu'il produit au niveau d'exigence d'un développeur expérimenté et intransigeant : une implémentation approximative est inacceptable, qu'un contrôle la signale ou non.
  - **Même exigence pour tout le code** : code de l'application, tests, scripts, outillage, configuration, workflows. Un test mal écrit ne garantit plus la non-régression qu'il porte, et rend instable ce qu'il vérifie.
  - **Usage documenté de chaque outil** : avant d'employer un outil, une bibliothèque ou une API, l'agent prend connaissance, dans sa documentation officielle, des pratiques qu'elle recommande et de celles qu'elle déconseille (cycle de vie des objets, libération des ressources, façons d'attendre, pièges signalés), et pas seulement de l'appel dont il a besoin ([Exploitation des technologies retenues](../../contraintes-techniques/exploitation-des-technologies-retenues.md), [Règles de travail de l'agent](regles-de-travail-de-l-agent.md)). Un usage que la documentation déconseille n'est retenu qu'avec sa justification dans `choix-implementation/`.
  - **Ressources libérées** : toute ressource que le code ouvre (connexion, contexte ou page d'un navigateur, flux, fichier, client, processus, conteneur) a un propriétaire, qui la libère explicitement dès qu'elle ne sert plus. Un code qui ouvre une ressource sans la libérer est défectueux, même si rien ne le signale encore.
  - **La cause de fond, toujours** : tout problème (bug, test instable, échec du CI, comportement inattendu, retour de revue, ticket à ouvrir) se traite par l'analyse de sa **cause de fond**, et jamais autrement. L'agent établit le mécanisme exact par des faits vérifiés (code, exécution, comparaison de ce qui est obtenu et de ce qui est attendu), nomme la cause, recense tout ce qu'elle touche, dans l'application comme dans les tests, et la corrige elle, pour que le problème ne puisse plus se produire : jamais un correctif limité au symptôme constaté (« sparadrap »), au cas relevé ou au seul passage en échec. Un ticket ouvert sur un problème porte cette analyse et la correction de la cause, jamais le seul symptôme avec une analyse renvoyée à plus tard ; des tickets successifs sur le même sujet signalent une cause qui n'a pas été atteinte. Les retours de revue en sont un cas particulier ([Revue Codex (bloquante)](../revue-tickets/revue-codex-bloquante.md#traiter-un-retour), corriger à la racine).
  - **Le code de l'application est écrit avant tout pour l'application** : sa conception suit le besoin et la documentation officielle des outils, et les tests ne dictent jamais comment il est écrit. Il peut être légèrement aménagé pour aider les tests (ex. une horloge remplaçable), sans que sa conception en dépende ; un test qui ne sait pas exercer la forme juste du code s'adapte à elle, par l'outil employé selon sa documentation ou par une doublure dans les tests (ex. un envoi de fichiers détaché du choix qui le lance, parce que l'outil de test bloquait sur un traitement attendu, interdit, #369) (exigence de l'utilisateur).
  - **Son propre code d'abord** : face à un comportement anormal ou instable (test instable, lenteur, délai dépassé), l'agent relit d'abord son propre code, et l'usage qu'il fait des outils au regard de leur documentation, avant de mettre en cause un outil largement adopté, son moteur ou l'environnement.
  - **Relecture exigeante** : avant de présenter un travail comme terminé, et avant tout push, l'agent le relit comme le ferait un relecteur exigeant, documentation à l'appui. Il ne compte ni sur la revue de code ni sur le CI pour trouver ce qu'il aurait dû voir.
  - **Rendu vérifié par l'agent** : toute création ou modification qui a un aspect visuel est vérifiée par l'agent lui-même sur son rendu, avant de la soumettre à l'utilisateur : la page affichée, sur grand écran et sur smartphone, dans au moins deux thèmes, comparée au résultat attendu (maquette, `visuel/`), et corrigée tant qu'elle s'en écarte. Les tests, qui vérifient structure et comportement, ne voient pas le rendu ; les captures de référence ne se comparent qu'après la validation. C'est une part de son travail, jamais une étape de la validation fonctionnelle ([Validation fonctionnelle](../revue-tickets/validation-fonctionnelle.md)), dont elle ne tient pas lieu et qu'elle ne remplace pas auprès de l'utilisateur : l'utilisateur contrôle, il ne vérifie pas à la place de l'agent (exigence de l'utilisateur).
- **Pragmatisme : on ne cherche pas le code parfait.** L'exigence de rigueur porte sur un code correct, simple et vérifié, pas sur un code parfait : la solution retenue est la plus simple qui répond au besoin réel, et le travail s'arrête dès qu'elle y répond, vérifiée dans la proportion de son risque (non-régression, ci-dessous). Ne sont jamais une raison de poursuivre : un mécanisme de plus pour un cas que la solution rend déjà rare et sans effet visible, la réécriture répétée d'un code ou d'un test qui fait déjà ce qu'on attend de lui, la recherche d'une forme idéale. Une conception qui se complique au fil des corrections signale une mauvaise piste : l'agent revient alors au besoin et à la règle la plus simple qui le satisfait, plutôt que d'ajouter un mécanisme de plus.
- Le projet est guidé par les principes **KISS, DRY, YAGNI et SOLID**. Toute décision (architecture, conception, implémentation, revue) doit s'y conformer :
  - **KISS** (*Keep It Simple, Stupid*) : privilégier la solution la plus simple qui répond au besoin réel, éviter la complexité non justifiée.
  - **DRY** (*Don't Repeat Yourself*) : éviter la duplication de logique ou de connaissance ; factoriser lorsque c'est pertinent, sans sur-factoriser prématurément.
  - **YAGNI** (*You Aren't Gonna Need It*) : ne pas implémenter de fonctionnalité, abstraction ou paramétrage anticipant un besoin futur non avéré.
  - **SOLID** : respecter les cinq principes de conception orientée objet (responsabilité unique, ouvert/fermé, substitution de Liskov, ségrégation des interfaces, inversion des dépendances) dans l'organisation du code.
- Le code doit suivre les **best practices communément admises** pour chaque technologie utilisée (conventions de nommage, patterns architecturaux, sécurité, performance, etc.). Ces best practices sont à vérifier via les sources officielles (cf. règle ci-dessus).
- **Méthodologie TDD (Test-Driven Development)** : toute implémentation de logique métier ou technique non triviale suit le cycle **Red → Green → Refactor** : écrire d'abord un test qui échoue pour le comportement visé (Red), écrire ensuite le code de production minimal qui le fait passer (Green), puis refactoriser le code — production et tests — une fois au vert (Refactor). Le test est **toujours écrit avant** le code qu'il vérifie, jamais après-coup pour documenter un comportement déjà implémenté.
- **Non-régression** : toute modification doit être accompagnée d'un moyen de vérifier qu'elle ne sera pas silencieusement annulée par une modification future. Le moyen de contrôle (test unitaire, test d'intégration, test de contrat, assertion, etc.) doit être **proportionné à la portée et au risque de la modification** : on n'écrit pas une suite de tests complète pour un changement trivial, mais toute logique métier ou technique non triviale doit être couverte — et développée selon le cycle TDD ci-dessus. La règle vaut pour tout livrable, ce que l'utilisateur voit et utilise compris (écrans, comportements, rendu) : la validation fonctionnelle de l'utilisateur ([Validation fonctionnelle](../revue-tickets/validation-fonctionnelle.md)) n'en tient jamais lieu. Elle accepte un comportement à un instant donné ; le moyen de contrôle le garantit dans la durée. Tout comportement validé est donc fixé par ce moyen dans la Pull Request qui le réalise.
  - **Tests qui ont un facteur temps, validés sur plusieurs exécutions** : un test dont le résultat dépend du temps (attente d'un rendu, d'un traitement asynchrone, d'un délai ou d'une horloge, navigateur, conteneur, réseau) peut passer une fois et échouer la suivante, selon l'ordre dans lequel les choses se produisent. Un tel test, ajouté ou modifié, ou dont le code exercé change, n'est donc tenu pour bon qu'après avoir réussi sur **plusieurs exécutions** successives, dont certaines sous une charge comparable à celle du CI (suites lancées en parallèle), avant le push qui le porte : une seule réussite ne prouve pas l'absence d'un problème de synchronisation. Un seul échec sur ces exécutions est un problème de synchronisation, traité à sa cause (ci-dessus, « La cause de fond, toujours »), jamais par une attente allongée (exigence de l'utilisateur).
- L'agent est **seul décisionnaire** sur l'architecture et l'implémentation : toute refactorisation jugée nécessaire (lisibilité, maintenabilité, testabilité, séparation des responsabilités, etc.) doit être faite sans attendre de validation.
- Le code doit être **propre et lisible** : l'utilisateur est développeur et lit le code produit.
- **Règle de commentaires** : les commentaires expliquent le **pourquoi** (intention, contrainte, décision de conception), jamais le **quoi** (ce que le code fait — le code se lit de lui-même).
- **Langue des fichiers techniques** : tout le contenu technique (code, noms de fonctions/classes/variables/constantes, commentaires, messages de log, noms de fichiers de configuration) est rédigé en **anglais**. Seule la documentation du projet (`.speckit/`, `README.md`, `README.dev.md`, etc.) est rédigée en **français**. Les messages destinés à l'utilisateur final sont produits par le système de traduction du frontend (cf. [Internationalisation](../../choix-implementation/socle/transverse/internationalisation.md)), pas codés en dur dans une langue donnée.
