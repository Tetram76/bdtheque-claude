# Outillage de développement

Outillage de développement .NET : gestion des packages, tests, couverture, validation des commentaires, cohérence des migrations et pipeline CI.

---

## Outillage de développement .NET

- **Gestion centralisée des packages NuGet** via `Directory.Packages.props` (Central Package Management) : toutes les versions sont déclarées à la racine de la solution, les fichiers `.csproj` ne référencent que les noms de package.
- **Tests unitaires et d'intégration** : `xunit`, exécutés via `dotnet test`. Les références communes des projets de test (`xunit`, son exécuteur, `Microsoft.NET.Test.Sdk`, `coverlet.collector`) sont déclarées une seule fois, dans `tests/Directory.Build.props`, pour les seuls projets de test (`*.Tests`), et non pour la bibliothèque qu'ils partagent (`Bdtheque.Testing`).
- **Couverture de code** : collectée par l'analyse SonarQube Cloud (`gestion-projet/depot.md` § Analyse de la qualité du code) avec `coverlet.collector`, au format OpenCover que lit son scanner pour C#, sur le code de l'application seul. `Bdtheque.Testing` est exclu de la collecte, et tout projet de `tests/` est déclaré comme code de test au scanner (`SonarQubeTestProject`, `tests/Directory.Build.props`) : la bibliothèque partagée par les tests ne référence aucun framework de test, et serait sinon analysée comme code de l'application. SonarQube Cloud présente la couverture parmi ses indicateurs (`README.md`, commentaire de chaque Pull Request). Elle informe, sans seuil qui ferait échouer le CI : la non-régression se juge sur ce que vérifient les tests, proportionnés à chaque modification (`gestion-projet/gouvernance.md` § Qualité du code), et non sur un pourcentage de lignes exécutées.
  - **Alternative écartée (collecte aussi par le CI, publiée dans son artefact)** : une seconde mesure de la même couverture, dans un autre format, que rien ne présente, et dont les réglages devraient être tenus alignés sur ceux de l'analyse.
  - **Scripts JavaScript du frontend** (`wwwroot`) : exclus de cette mesure (`gestion-projet/depot.md` § Analyse de la qualité du code), qui ne voit que le code .NET exécuté par les tests ; ils s'exécutent dans le navigateur, où leurs comportements sont fixés par les tests de bout en bout (§ Outillage de développement .NET, tests du frontend). Exclus, ils ne sont pas dispensés de tests : seul leur pourcentage n'est pas mesuré.
    - **Alternative écartée (mesure de leur couverture)** : Chromium relève le JavaScript exécuté (couverture des scripts, accessible par Playwright), mais SonarQube Cloud ne lit pour le JavaScript qu'un rapport LCOV, dont la conversion depuis le format de Chromium demande un outil Node.js (ex. `v8-to-istanbul`), absent de la chaîne de construction, ou un convertisseur écrit pour le projet ; soit une chaîne d'outillage de plus, pour un seul script d'une trentaine de lignes. À reconsidérer dès que les scripts du frontend ne se limitent plus à quelques fichiers courts, la mesure de leur couverture signalant alors les comportements qu'aucun test ne fixe.
- **Tests de persistance et d'intégration de l'API sur PostgreSQL réel** : `Testcontainers.PostgreSql` démarre, par exécution de tests, un conteneur de la **même image** que le service `db` de `docker-compose.yml` (alignement vérifié par un test) ; le schéma y est produit par les **migrations** (jamais par `EnsureCreated`), et chaque test dispose de sa propre base, clonée d'une base modèle migrée une fois (`CREATE DATABASE … TEMPLATE`), dont les connexions sont libérées à la fin du test (une base par test, donc un pool de connexions par test : conservées, elles épuiseraient `max_connections`). Les tests de l'API (`Microsoft.AspNetCore.Mvc.Testing`, `WebApplicationFactory`) démarrent sur une base vide, comme un premier déploiement, par un hôte de l'API partagé avec les tests de bout en bout (`ApiHostFactory`, `Bdtheque.Testing`), sans référence à un framework de test. Docker est donc requis pour exécuter les tests, localement comme en CI.
  - **Alternative écartée (SQLite en mémoire)** : un autre moteur que celui de production ne vérifie ni les migrations réellement appliquées, ni la collation (tri linguistique), ni la précision des `decimal`, ni la forme exacte des contraintes PostgreSQL — précisément ce que ces tests doivent garantir. Son seul avantage (pas de dépendance à Docker) ne compense pas des tests verts sur un schéma qui n'est pas celui livré.
- **Tests du frontend** (non-régression de ce que l'utilisateur voit et utilise, `gestion-projet/gouvernance.md` § Qualité du code) : deux niveaux, exécutés par `dotnet test` avec le reste des tests, en local avant tout push comme par le CI.
  - **Tests des composants** (`Bdtheque.Frontend.Tests`) : **bUnit** (licence MIT, projet de la .NET Foundation), qui rend un composant Blazor en mémoire, sans navigateur, et en vérifie le balisage et le comportement : affichage selon les données, paramètres, liens, saisie et réactions d'un composant interactif. La logique non triviale du frontend sans composant (ex. `ReturnPath`) y a ses tests unitaires.
  - **Tests de bout en bout** (`Bdtheque.EndToEnd.Tests`) : **Playwright** pour .NET (`Microsoft.Playwright`, licence Apache 2.0, Microsoft), qui pilote Chromium sur l'**application complète** : `frontend` écoute sur un vrai port (`WebApplicationFactory.UseKestrel`, .NET 10), un navigateur ne pouvant joindre un serveur de test en mémoire, et appelle `api`, elle-même sur sa base PostgreSQL (`ApiHostFactory`, `Bdtheque.Testing`), par un client HTTP dont le gestionnaire est celui du serveur de test d'`api`, comme le réseau Docker porte ses appels. `frontend` y tourne en environnement `Production`, comme déployé, mais sert les fichiers statiques du build (`UseStaticWebAssets`), ceux de la publication n'existant pas lors des tests : sans eux, les pages n'auraient ni styles ni script de Blazor, ce que vérifie `StaticAssetsTests`. Ils vérifient ce que seul un navigateur exerce : navigation, redirections, rendu statique et interactif, cookies, et chaque comportement des scripts du frontend (`wwwroot`), que la couverture des tests .NET ne mesure pas. Le navigateur est installé par les tests eux-mêmes s'il manque (aucune étape manuelle en local) ; le CI installe en outre les bibliothèques système qu'il exige (`playwright.ps1 install --with-deps chromium`), dans le job des tests, sans job supplémentaire.
  - **Composants partagés par les écrans** : présentés dans un navigateur, avant qu'un écran les emploie, par des pages des tests seuls (`Bdtheque.EndToEnd.Tests` : `ControlsPage` pour les contrôles ; `AdminFramePage` pour l'en-tête de l'administration, sans la connexion qu'exigent ses pages, et la navigation des listes), où leurs tests de bout en bout fixent ce que seul un navigateur fait (menus, dialogue modal, clavier du choix d'une fiche, lignes défilantes et leurs scripts, en-têtes collés en haut de l'écran, mise en page sur smartphone, styles des contrôles), et que les captures de référence fixent dans chaque thème. L'application route les pages des assemblages que lui déclare `PageAssemblies` : aucun en production, celui des tests de bout en bout dans leurs tests.
  - **Règle appliquée aux écrans** : le chantier qui réalise un écran fixe chacun de ses comportements par un test, dans la Pull Request qui le réalise, avant sa validation fonctionnelle : un test de composant pour ce que l'écran présente et pour chacun de ses états (données, absence de données, erreur), et au moins un test de bout en bout par parcours de l'utilisateur sur l'écran (arrivée, navigation vers et depuis l'écran, saisie et enregistrement, action interactive). Un retour de validation fonctionnelle qui modifie un comportement modifie son test. Les tests désignent les éléments par ce qui ne dépend pas du thème (rôle, lien et sa cible, structure de la page), jamais par l'apparence, pour que l'ajout ou la modification d'un thème ne les casse pas.
  - **Alternative écartée (Selenium)** : attentes à écrire à la main, sans l'attente automatique des éléments de Playwright, cause usuelle de tests instables.
  - **Alternative écartée (application complète en conteneurs, `docker compose`, pour les tests de bout en bout)** : une construction des images à chaque exécution, et des tests qui ne pourraient plus régler l'horloge de l'application ni ses données comme les tests de l'API le font.
- **Validation des commentaires XML** (`Directory.Build.props`) : le compilateur vérifie les commentaires de documentation (`GenerateDocumentationFile`), et un commentaire qui désigne un paramètre, un type ou un membre inexistant, ou qui est mal formé, mal placé ou en double, fait échouer la compilation : rien d'autre ne signalerait un commentaire devenu faux après une modification du code. Tout avertissement est traité en erreur (`TreatWarningsAsErrors`), plutôt qu'une liste choisie d'avertissements de documentation, qui laisserait passer ceux qu'elle oublie (ex. une balise `<param>` en double, `CS1571`) ; la compilation est de toute façon tenue sans avertissement. Documenter chaque membre (`CS1591`) ou chaque paramètre (`CS1573`) n'est pas exigé, les commentaires expliquant le pourquoi et non le quoi (`gestion-projet/gouvernance.md` § Qualité du code). Les fichiers de documentation ne servent qu'au compilateur et aux outils de développement, jamais à l'application : ils ne sont pas publiés (`PublishDocumentationFiles`), donc absents des images Docker.
- **Contrôle de cohérence modèle ↔ migrations** : la CI exécute `dotnet ef migrations has-pending-model-changes`, qui échoue si une modification du modèle EF a été commitée sans sa migration.
- **Étapes du pipeline CI** (`gestion-projet/depot.md` § Intégration continue (CI)) : installation du SDK, à la version exacte de l'image `sdk` des Dockerfiles, restauration, build en mode `Release`, contrôle de cohérence modèle ↔ migrations, installation du navigateur des tests de bout en bout (§ Outillage de développement .NET, tests du frontend), exécution de la totalité des tests (`dotnet test`, sur PostgreSQL via Testcontainers — Docker est disponible sur les runners `ubuntu-latest`), puis publication des résultats ; la couverture est mesurée par l'analyse SonarQube Cloud (§ Outillage de développement .NET, couverture de code).
  - **Tests exécutés aussi par l'analyse SonarQube Cloud** : l'analyse (`code-quality.yml`) exécute de nouveau la totalité des tests, sur la compilation qu'instrumente son scanner, pour en mesurer la couverture (§ Outillage de développement .NET, couverture de code). Elle tourne en parallèle du CI, dont elle n'allonge pas la durée. Le CI garde sa propre exécution : ses checks requis disent seuls si la non-régression est confirmée, que SonarQube Cloud et son jeton soient disponibles ou non.
    - **Alternative écartée (une seule exécution des tests, par un job qui enchaîne la compilation stricte puis l'analyse)** : un téléchargement de l'image PostgreSQL des tests de moins par exécution (`gestion-projet/depot.md` § Intégration continue (CI), quotas), mais le check de la non-régression échouerait avec l'analyse (service en panne, jeton absent), sans qu'on distingue une régression d'une analyse indisponible, et ses deux compilations successives en allongeraient l'attente.
  - **Version du SDK** : déclarée, à l'identique, par l'image `sdk` des deux Dockerfiles et par chaque workflow qui installe le SDK (`dotnet-version`), alignement vérifié par `SdkVersionTests`. `global.json` n'en fixe que le minimum, avec une montée vers toute version ultérieure de .NET 10 (`latestFeature`), pour que les postes de développement gardent le SDK de leur environnement (ex. celui de Visual Studio).
    - **Alternative écartée (version lue dans `global.json` par `actions/setup-dotnet`, entrée `global-json-file`)** : avec une montée `latest…`, l'action installe la dernière version du canal (`10.0`), qui change sans modification du dépôt (`gestion-projet/depot.md` § Mises à jour des dépendances) ; avec une version exacte, `global.json` l'imposerait à chaque poste de développement.
  - **Cache NuGet** : le dossier des packages est mis en cache (`actions/cache`), sous une clé tirée de tout ce qui décide des packages restaurés : version du SDK, qui apporte des packages implicites, `Directory.Packages.props`, fichiers `Directory.Build.props` et projets, outils (`dotnet-tools.json`). Sans clé de repli : un cache partiel, complété puis enregistré sous la nouvelle clé, garderait les packages de toutes les versions passées.
  - **Restauration non verrouillée** : la restauration se fonde sur les versions exactes de `Directory.Packages.props`, épinglage des dépendances transitives compris (`CentralPackageTransitivePinningEnabled`), sans fichiers de verrouillage NuGet.
    - **Alternative écartée (fichiers de verrouillage, `packages.lock.json`, restauration `--locked-mode`)** : le fichier du frontend porte un package implicite dont la version est celle du SDK qui restaure (`Microsoft.AspNetCore.App.Internal.Assets`, constaté : `10.0.11` avec le SDK `10.0.303`), si bien qu'une restauration verrouillée échoue avec tout autre SDK (`NU1004`, `dotnet/sdk` demande n° 48795). La documentation de `global.json` prescrit alors une version exacte du SDK (`rollForward: disable`) sur chaque poste et dans le CI, et chaque version corrective du SDK imposerait de régénérer les fichiers. Leur apport, une restauration reproductible, est déjà acquis par les versions exactes de la gestion centralisée, les packages de nuget.org n'étant jamais remplacés sous une même version.
  - **Exécutions annulées** : une nouvelle exécution sur une Pull Request annule celle, devenue inutile, de son commit précédent (`concurrency`, `cancel-in-progress`), pour ne pas consommer les quotas de Docker Hub et de l'API GitHub (`gestion-projet/depot.md` § Intégration continue (CI)). Une exécution sur `main` n'est jamais annulée ni mise en attente : chacune a son propre groupe.
