# Outillage de développement

Outillage de développement .NET : gestion des packages, tests, couverture, validation des commentaires, cohérence des migrations et pipeline CI.

---

## Outillage de développement .NET

- **Gestion centralisée des packages NuGet** via `Directory.Packages.props` (Central Package Management) : toutes les versions sont déclarées à la racine de la solution, les fichiers `.csproj` ne référencent que les noms de package.
- **Tests unitaires et d'intégration** : `xunit`, exécutés via `dotnet test`. Les références communes des projets de test (`xunit`, son exécuteur, `Microsoft.NET.Test.Sdk`, `coverlet.collector`) sont déclarées une seule fois, dans `tests/Directory.Build.props`, pour les seuls projets de test (`*.Tests`), et non pour la bibliothèque qu'ils partagent (`Bdtheque.Testing`).
- **Couverture de code** : collectée par l'unique exécution des tests du CI, avec `coverlet.collector`, au format OpenCover que lit le scanner de SonarQube Cloud pour C#, sur le code de l'application seul, puis analysée par le job de l'analyse ([Analyse de la qualité du code](../gestion-projet/depot/analyse-de-la-qualite-du-code.md)). `Bdtheque.Testing` est exclu de la collecte, et tout projet de `tests/` est déclaré comme code de test au scanner (`SonarQubeTestProject`, `tests/Directory.Build.props`) : la bibliothèque partagée par les tests ne référence aucun framework de test, et serait sinon analysée comme code de l'application. SonarQube Cloud présente la couverture parmi ses indicateurs (`README.md`, commentaire de chaque Pull Request). Elle informe, sans seuil qui ferait échouer le CI : la non-régression se juge sur ce que vérifient les tests, proportionnés à chaque modification ([Qualité du code](../gestion-projet/gouvernance/qualite-du-code.md)), et non sur un pourcentage de lignes exécutées.
  - **Scripts JavaScript du frontend** (`wwwroot`) : exclus de cette mesure ([Analyse de la qualité du code](../gestion-projet/depot/analyse-de-la-qualite-du-code.md)), qui ne voit que le code .NET exécuté par les tests ; ils s'exécutent dans le navigateur, où leurs comportements sont fixés par les tests de bout en bout ([Outillage de développement .NET](outillage.md), tests du frontend). Exclus, ils ne sont pas dispensés de tests : seul leur pourcentage n'est pas mesuré.
    - **Alternative écartée (mesure de leur couverture)** : Chromium relève le JavaScript exécuté (couverture des scripts, accessible par Playwright), mais SonarQube Cloud ne lit pour le JavaScript qu'un rapport LCOV, dont la conversion depuis le format de Chromium demande un outil Node.js (ex. `v8-to-istanbul`), absent de la chaîne de construction, ou un convertisseur écrit pour le projet ; soit une chaîne d'outillage de plus, pour un seul script d'une trentaine de lignes. À reconsidérer dès que les scripts du frontend ne se limitent plus à quelques fichiers courts, la mesure de leur couverture signalant alors les comportements qu'aucun test ne fixe.
- **Tests de persistance et d'intégration de l'API sur PostgreSQL réel** : `Testcontainers.PostgreSql` démarre, par exécution de tests, un conteneur de la **même image** que le service `db` de `docker-compose.yml` (alignement vérifié par un test) ; le schéma y est produit par les **migrations** (jamais par `EnsureCreated`), et chaque test dispose de sa propre base, clonée d'une base modèle migrée une fois (`CREATE DATABASE … TEMPLATE`), dont les connexions sont libérées à la fin du test (une base par test, donc un pool de connexions par test : conservées, elles épuiseraient `max_connections`). Les tests de l'API (`Microsoft.AspNetCore.Mvc.Testing`, `WebApplicationFactory`) démarrent sur une base vide, comme un premier déploiement, par un hôte de l'API partagé avec les tests de bout en bout (`ApiHostFactory`, `Bdtheque.Testing`), sans référence à un framework de test. Docker est donc requis pour exécuter les tests, localement comme en CI.
  - **Alternative écartée (SQLite en mémoire)** : un autre moteur que celui de production ne vérifie ni les migrations réellement appliquées, ni la collation (tri linguistique), ni la précision des `decimal`, ni la forme exacte des contraintes PostgreSQL — précisément ce que ces tests doivent garantir. Son seul avantage (pas de dépendance à Docker) ne compense pas des tests verts sur un schéma qui n'est pas celui livré.
- **Tests du frontend** (non-régression de ce que l'utilisateur voit et utilise, [Qualité du code](../gestion-projet/gouvernance/qualite-du-code.md)) : deux niveaux, exécutés par `dotnet test` avec le reste des tests, en local avant tout push comme par le CI.
  - **Tests des composants** (`Bdtheque.Frontend.Tests`) : **bUnit** (licence MIT, projet de la .NET Foundation), qui rend un composant Blazor en mémoire, sans navigateur, et en vérifie le balisage et le comportement : affichage selon les données, paramètres, liens, saisie et réactions d'un composant interactif. Un composant qui attend un délai (ex. la pause de la frappe du choix d'une fiche) le fait sur l'horloge `TimeProvider` de l'application, que ses tests remplacent par l'horloge factice de Microsoft (`FakeTimeProvider`, `Microsoft.Extensions.TimeProvider.Testing`, licence MIT), avancée par le test : aucune attente réelle, ni dépendance au moment où le test s'exécute. La logique non triviale du frontend sans composant (ex. `ReturnPath`) y a ses tests unitaires.
  - **Tests de bout en bout** (`Bdtheque.EndToEnd.Tests`) : **Playwright** pour .NET (`Microsoft.Playwright`, licence Apache 2.0, Microsoft), qui pilote Chromium sur l'**application complète** : `frontend` écoute sur un vrai port (`WebApplicationFactory.UseKestrel`, .NET 10), un navigateur ne pouvant joindre un serveur de test en mémoire, et appelle `api`, elle-même sur sa base PostgreSQL (`ApiHostFactory`, `Bdtheque.Testing`), par un client HTTP dont le gestionnaire est celui du serveur de test d'`api`, comme le réseau Docker porte ses appels. `frontend` y tourne en environnement `Production`, comme déployé, mais sert les fichiers statiques du build (`UseStaticWebAssets`), ceux de la publication n'existant pas lors des tests : sans eux, les pages n'auraient ni styles ni script de Blazor, ce que vérifie `StaticAssetsTests`. Ils vérifient ce que seul un navigateur exerce : navigation, redirections, rendu statique et interactif, cookies, et chaque comportement des scripts du frontend (`wwwroot`), que la couverture des tests .NET ne mesure pas. Les tests s'exécutent sans fenêtre, dans le navigateur sans interface de Chromium (*headless shell*) : seul celui-ci est installé (`--only-shell`, que la documentation de Playwright prescrit dans ce cas), ni le Chromium complet, qui ne sert qu'avec une fenêtre, ni FFmpeg, qui ne sert qu'à une vidéo. Il est installé par les tests eux-mêmes s'il manque (aucune étape manuelle en local) ; le CI installe en outre les bibliothèques système qu'il exige (`playwright.ps1 install --with-deps --only-shell chromium`), dans le job des tests, sans job supplémentaire.
    - **Alternative écartée (cache des navigateurs, `actions/cache`)** : la documentation de Playwright le déconseille, sa restauration prenant autant que le téléchargement, et les bibliothèques système, la plus grande part de l'installation, ne se mettent pas en cache.
  - **Pilotage du navigateur** ([Qualité du code](../gestion-projet/gouvernance/qualite-du-code.md), usage documenté des outils et ressources libérées) : chaque test possède les contextes du navigateur qu'il ouvre (`BrowserTest`), et les ferme à sa fin avec leurs pages, comme la documentation de Playwright le prescrit pour un contexte créé directement : ouverts, ils s'accumuleraient au fil d'un passage avec leurs connexions à l'application et, sur le serveur, les circuits de leurs composants interactifs. Une page est jugée prête sur son propre état (`PageReadiness`), et jamais sur le silence du réseau (`NetworkIdle`, que la documentation déconseille pour les tests) ni sur une attente fixe : chargement (document complet, `document.readyState`), chaque feuille de style appliquée (une feuille qui n'a pu être chargée fait échouer le test, qui ne vérifierait sinon qu'une page que personne ne voit), polices disposées, dessin du script du thème achevé, puis deux images, au terme desquelles ce que les scripts font une fois la page disposée (observateurs des tailles et des mutations, dessins reportés à l'image suivante) est fait. Une page qui n'est pas prête dans le délai fait échouer le test en nommant les requêtes en échec et celles encore en cours, qui retiennent son chargement. Un composant interactif est attendu par ce qu'il fait une fois rendu par son circuit (ex. le module du choix d'une fiche, importé après son premier rendu interactif), jamais par des essais répétés.
    - **Attentes vérifiées par le pilote, en un seul appel** : une attente porte sur ce que le pilote de Playwright vérifie lui-même : arrivée à une adresse (`Assertions.Expect(page).ToHaveURLAsync`, adresses attendues de `PageAddress`), condition dans la page (`WaitForFunctionAsync`), chargement d'une navigation (`GotoAsync`, `ReloadAsync`). Le client .NET de Playwright attend un état de chargement ou une navigation en deux temps : il vérifie les états qu'il a reçus, puis s'abonne aux suivants, qu'un autre fil lui livre ; un état arrivé entre les deux est perdu, et l'attente court jusqu'à son délai, la page chargée (défaut ouvert en 1.64.1 : [`microsoft/playwright-dotnet` #3364](https://github.com/microsoft/playwright-dotnet/issues/3364) et [#3399](https://github.com/microsoft/playwright-dotnet/issues/3399) ; constaté sur la capture de l'accueil de l'administration, #298). Ces attentes du client (`WaitForLoadStateAsync`, `WaitForURLAsync`, `WaitForNavigationAsync`, `RunAndWaitForNavigationAsync`) sont refusées par le compilateur dans les tests de bout en bout (`BannedSymbols.txt`, analyseur `Microsoft.CodeAnalysis.BannedApiAnalyzers` de Roslyn, licence MIT, diagnostic `RS0030`), tant qu'une version du client n'a pas corrigé le défaut : la montée de version de Playwright le vérifie.
      - **Alternative écartée (attente répétée par tranches courtes, remède proposé dans le signalement)** : elle retrouve l'état perdu à la tranche suivante, mais garde, sous une relance, une attente qui en perd ; une attente vérifiée par le pilote n'en perd aucun.
      - **Alternative écartée (test du dépôt qui cherche ces noms dans les sources des tests)** : il confondrait un appel avec sa mention dans un commentaire ; l'analyseur ne voit que les appels, à la compilation.
  - **Composants partagés par les écrans** : présentés dans un navigateur, avant qu'un écran les emploie, par des pages des tests seuls (`Bdtheque.EndToEnd.Tests` : `ControlsPage` pour les contrôles ; `AdminFramePage` pour l'en-tête de l'administration, sans la connexion qu'exigent ses pages, et la navigation des listes), où leurs tests de bout en bout fixent ce que seul un navigateur fait (menus, dialogue modal, clavier du choix d'une fiche, lignes défilantes et leurs scripts, en-têtes collés en haut de l'écran, mise en page sur smartphone, styles des contrôles), et que les captures de référence fixent dans chaque thème. L'application route les pages des assemblages que lui déclare `PageAssemblies` : aucun en production, celui des tests de bout en bout dans leurs tests.
  - **Règle appliquée aux écrans** : le chantier qui réalise un écran fixe chacun de ses comportements par un test, dans la Pull Request qui le réalise, avant sa validation fonctionnelle : un test de composant pour ce que l'écran présente et pour chacun de ses états (données, absence de données, erreur), et au moins un test de bout en bout par parcours de l'utilisateur sur l'écran (arrivée, navigation vers et depuis l'écran, saisie et enregistrement, action interactive). Un retour de validation fonctionnelle qui modifie un comportement modifie son test. Les tests désignent les éléments par ce qui ne dépend pas du thème (rôle, lien et sa cible, structure de la page), jamais par l'apparence, pour que l'ajout ou la modification d'un thème ne les casse pas.
  - **Écran qui dépend de toute la collection** (ex. l'accueil, [Page d'accueil](../fonctionnel/page-accueil.md)) : ses tests de bout en bout et ses captures tournent sur une application de test qui lui est propre (`ApplicationHost`, données écrites par `SeedAsync` au travers de l'API), une par état présenté (collection vide, collection garnie) : la base partagée des autres tests reçoit leurs propres données, qui changeraient son rendu selon l'ordre d'exécution.
  - **Alternative écartée (Selenium)** : attentes à écrire à la main, sans l'attente automatique des éléments de Playwright, cause usuelle de tests instables.
  - **Alternative écartée (application complète en conteneurs, `docker compose`, pour les tests de bout en bout)** : une construction des images à chaque exécution, et des tests qui ne pourraient plus régler l'horloge de l'application ni ses données comme les tests de l'API le font.
- **Validation des commentaires XML** (`Directory.Build.props`) : le compilateur vérifie les commentaires de documentation (`GenerateDocumentationFile`), et un commentaire qui désigne un paramètre, un type ou un membre inexistant, ou qui est mal formé, mal placé ou en double, fait échouer la compilation : rien d'autre ne signalerait un commentaire devenu faux après une modification du code. Tout avertissement est traité en erreur (`TreatWarningsAsErrors`), plutôt qu'une liste choisie d'avertissements de documentation, qui laisserait passer ceux qu'elle oublie (ex. une balise `<param>` en double, `CS1571`) ; la compilation est de toute façon tenue sans avertissement. Documenter chaque membre (`CS1591`) ou chaque paramètre (`CS1573`) n'est pas exigé, les commentaires expliquant le pourquoi et non le quoi ([Qualité du code](../gestion-projet/gouvernance/qualite-du-code.md)). Les fichiers de documentation ne servent qu'au compilateur et aux outils de développement, jamais à l'application : ils ne sont pas publiés (`PublishDocumentationFiles`), donc absents des images Docker.
- **Contrôle de cohérence modèle ↔ migrations** : la CI exécute `dotnet ef migrations has-pending-model-changes`, qui échoue si une modification du modèle EF a été commitée sans sa migration.
- **Étapes du pipeline CI** ([Intégration continue (CI)](../gestion-projet/depot/integration-continue-ci.md)) : installation du SDK, à la version exacte de l'image `sdk` des Dockerfiles, restauration, build en mode `Release`, contrôle de cohérence modèle ↔ migrations, installation du navigateur des tests de bout en bout ([Outillage de développement .NET](outillage.md), tests du frontend), exécution des tests (`dotnet test`, sur PostgreSQL via Testcontainers — Docker est disponible sur les runners `ubuntu-latest`) avec la collecte de leur couverture ([Outillage de développement .NET](outillage.md), couverture de code), puis publication des résultats et de la couverture, en artefacts.
  - **Tests selon la modification** ([Intégration continue (CI)](../gestion-projet/depot/integration-continue-ci.md)) : la première étape du job des tests classe les fichiers que modifie la Pull Request, et les étapes suivantes en dépendent. Ces fichiers sont ceux qui distinguent le commit de fusion que le CI construit (`refs/pull/<numéro>/merge`, documentation GitHub) de son premier parent, la tête de `main` qu'il fusionne : la Pull Request telle qu'elle serait fusionnée, au regard de `main` tel qu'il est. Le dépôt est donc récupéré sur deux commits (`fetch-depth: 2`), et la comparaison ne détecte pas les déplacements (`--no-renames`), pour qu'un fichier déplacé compte à ses deux chemins.
    - **Aucune source modifiée** : après la restauration et la compilation, inchangées (celle de la solution coûte à peine plus que celle des projets qu'exigent les tests du dépôt, qui en référencent presque tous les projets), seuls les tests du dépôt s'exécutent, désignés par leur trait (`[Trait("Category", "Repository")]`, filtre `Category=Repository`) ; tout test qui lit un fichier du dépôt (`RepositoryFiles`) le porte. Ni contrôle des migrations, ni navigateur, ni relevé du réseau, ni conteneur, ni couverture : l'analyse SonarQube Cloud s'exécute sans rapport de couverture, la Pull Request n'ayant modifié aucun code que celle-ci mesure.
    - **Aucune source du rendu modifiée** : l'étape des tests de bout en bout, captures comprises, est omise, comme l'installation du navigateur, le réglage des interfaces de Docker et le relevé du réseau, qui ne servent qu'à elle.
    - **Alternative écartée (action de filtrage par chemins, ex. `dorny/paths-filter`)** : une dépendance de plus à épingler et à surveiller ([Suivi des versions et des vulnérabilités](../contraintes-techniques/suivi-des-versions-et-des-vulnerabilites.md)), pour une comparaison que `git` fait en une commande.
  - **Interfaces de Docker sans adresse de lien local** : Chromium abandonne les requêtes des pages qu'il charge dès qu'une adresse de la machine est ajoutée ou retirée, sur quelque interface que ce soit (`net::ERR_NETWORK_CHANGED` ; `AddressTrackerLinux`, qui suit pour cela les messages netlink de toutes les interfaces). Sur l'exécuteur, les seuls changements d'adresse pendant les tests sont ceux des interfaces que Docker crée pour chaque conteneur (relevé du CI, #294) : le noyau donne à chacune une adresse IPv6 de lien local environ une seconde et demie après le démarrage du conteneur, et la retire avec lui. Or chaque processus de test démarre ses conteneurs (PostgreSQL et Ryuk, Testcontainers), que Ryuk ne supprime que dix secondes après la fin de ce processus (`RYUK_RECONNECTION_TIMEOUT`, documentation de Ryuk), sans que `dotnet test` l'attende : une page chargée à cet instant perd des requêtes (feuilles de style, scripts), et sa capture diffère de sa référence. Avant les tests, le CI règle donc la génération des adresses de lien local à « aucune » pour les interfaces que Docker créera (`net.ipv6.conf.default.addr_gen_mode=1`, que le noyau applique à toute interface créée ensuite, documentation du noyau, *IP Sysctl*) et pour son pont, déjà créé (`docker0`) : le pont par défaut de Docker n'emploie que l'IPv4, et aucune autre interface de la machine n'est touchée.
    - **Contrôle** : les changements de liens et d'adresses de l'exécuteur (`ip monitor`) et les évènements de Docker sont relevés pendant les tests ; une étape fait échouer le job si une interface de Docker a reçu ou perdu une adresse pendant ce temps, et le relevé est publié en artefact avec les résultats d'une exécution en échec, qui en donne les faits.
    - **Alternative écartée (tests de bout en bout exécutés seuls, après les autres ou avant eux, pour les tenir à l'écart des conteneurs)** : l'ordre des étapes déplace les changements d'adresse sans les supprimer. La suppression des conteneurs d'une étape tombe pendant la suivante, dix secondes après la fin de son processus (constaté, #294), et l'adresse des conteneurs des tests de bout en bout eux-mêmes apparaît après leur démarrage, au moment où peuvent se charger les premières pages.
    - **Alternative écartée (désactiver IPv6 sur l'exécuteur, remède proposé par des images de Puppeteer)** : elle modifie le réseau de toute la machine, quand seules les interfaces de Docker changent d'adresse.
    - **Alternative écartée (navigateur dans son propre espace réseau, en conteneur, comme les captures locales de `scripts/Test-Captures.ps1`)** : Chromium n'y verrait plus les interfaces de l'exécuteur, mais les tests de bout en bout devraient joindre depuis ce conteneur l'application qu'ils hébergent, pour un résultat que le réglage des seules interfaces de Docker obtient.
  - **Tests de bout en bout exécutés seuls, après les autres** : chaque test une seule fois, en deux étapes, les tests sans navigateur côte à côte, puis les tests de bout en bout seuls. Côte à côte avec les autres, ils durent deux fois plus longtemps (constaté sur le CI : 2 min 5 s au lieu d'une minute), faute de processeurs sur l'exécuteur, et s'approchent des délais de leur navigateur, sans que l'ensemble finisse plus tôt.
  - **Une seule exécution des tests par push** : le job de l'analyse SonarQube Cloud (`SonarQube Cloud analysis`, [Analyse de la qualité du code](../gestion-projet/depot/analyse-de-la-qualite-du-code.md)) suit celui des tests, dont il reprend la couverture, sur la compilation qu'instrumente son scanner, sans exécuter les tests de nouveau. Les deux restent des jobs distincts : le check des tests dit seul si la non-régression est confirmée, et une analyse qui ne peut pas aboutir (service en panne, jeton absent) fait échouer son propre job, jamais celui-là. Le scanner (`dotnet-sonarscanner`, outil local épinglé de `dotnet-tools.json`) désactive en outre `TreatWarningsAsErrors` dans la compilation qu'il instrumente : sa compilation ne peut pas remplacer la compilation stricte du job des tests.
    - **Alternative écartée (tests exécutés aussi par l'analyse, en parallèle du CI)** : elle n'allongeait pas l'attente du CI, mais doublait le temps d'exécuteur, les téléchargements de l'image PostgreSQL des tests ([Intégration continue (CI)](../gestion-projet/depot/integration-continue-ci.md), quotas), et la probabilité qu'une instabilité fasse échouer un push : la seconde exécution, ralentie par l'instrumentation de la couverture, pouvait échouer quand la première réussissait, et le check `SonarCloud Code Analysis`, faute d'analyse aboutie, n'était pas publié.
    - **Alternative écartée (un seul job qui enchaîne la compilation stricte, l'analyse et les tests)** : le check de la non-régression échouerait avec l'analyse, sans qu'on distingue une régression d'une analyse indisponible.
  - **Analyse d'une version publiée** ([Versions et releases](../gestion-projet/depot/versions-et-releases.md), publication) : le CI se lance aussi à la demande (`workflow_dispatch`), et l'analyse de `main` qui suit la pose d'un tag est relancée par `gh workflow run ci.yml --ref main` ; l'analyse n'étant qu'un job du CI, qui reprend la couverture de ses tests, c'est le CI entier qui s'exécute.
  - **Version du SDK** : déclarée, à l'identique, par l'image `sdk` des deux Dockerfiles et par chaque workflow qui installe le SDK (`dotnet-version`), alignement vérifié par `SdkVersionTests`. `global.json` n'en fixe que le minimum, avec une montée vers toute version ultérieure de .NET 10 (`latestFeature`), pour que les postes de développement gardent le SDK de leur environnement (ex. celui de Visual Studio).
    - **Alternative écartée (version lue dans `global.json` par `actions/setup-dotnet`, entrée `global-json-file`)** : avec une montée `latest…`, l'action installe la dernière version du canal (`10.0`), qui change sans modification du dépôt ([Mises à jour des dépendances](../gestion-projet/depot/mises-a-jour-des-dependances.md)) ; avec une version exacte, `global.json` l'imposerait à chaque poste de développement.
  - **Cache NuGet** : le dossier des packages est mis en cache (`actions/cache`), sous une clé tirée de tout ce qui décide des packages restaurés : version du SDK, qui apporte des packages implicites, `Directory.Packages.props`, fichiers `Directory.Build.props` et projets, outils (`dotnet-tools.json`). Sans clé de repli : un cache partiel, complété puis enregistré sous la nouvelle clé, garderait les packages de toutes les versions passées.
  - **Restauration non verrouillée** : la restauration se fonde sur les versions exactes de `Directory.Packages.props`, épinglage des dépendances transitives compris (`CentralPackageTransitivePinningEnabled`), sans fichiers de verrouillage NuGet.
    - **Alternative écartée (fichiers de verrouillage, `packages.lock.json`, restauration `--locked-mode`)** : le fichier du frontend porte un package implicite dont la version est celle du SDK qui restaure (`Microsoft.AspNetCore.App.Internal.Assets`, constaté : `10.0.11` avec le SDK `10.0.303`), si bien qu'une restauration verrouillée échoue avec tout autre SDK (`NU1004`, `dotnet/sdk` demande n° 48795). La documentation de `global.json` prescrit alors une version exacte du SDK (`rollForward: disable`) sur chaque poste et dans le CI, et chaque version corrective du SDK imposerait de régénérer les fichiers. Leur apport, une restauration reproductible, est déjà acquis par les versions exactes de la gestion centralisée, les packages de nuget.org n'étant jamais remplacés sous une même version.
  - **Exécutions annulées** : une nouvelle exécution sur une Pull Request annule celle, devenue inutile, de son commit précédent (`concurrency`, `cancel-in-progress`), pour ne pas consommer les quotas de Docker Hub et de l'API GitHub ([Intégration continue (CI)](../gestion-projet/depot/integration-continue-ci.md)). Une exécution sur `main` n'est jamais annulée ni mise en attente : chacune a son propre groupe.
