# Erreurs et suppressions

Erreurs métier, fonctionnelles et techniques, et suppression des entités.

---

## Erreurs métier, fonctionnelles et techniques

- Pour que l'utilisateur distingue une erreur métier d'une erreur technique (`fonctionnel/index.md` § Présentation des erreurs), le domaine signale **toute violation d'une règle métier** par un type dédié, `DomainRuleViolationException` (`Bdtheque.Domain.Common`), porteur d'un **code de règle stable** (`DomainRules`). Le texte présenté à l'utilisateur est produit à partir de ce code par la localisation du frontend ; le message de l'exception ne sert qu'aux journaux.
- Est **métier** toute erreur qu'une saisie de l'utilisateur peut provoquer et qu'il peut corriger (champ obligatoire vide, incohérence entre champs, cycle d'univers, intention d'achat en double…). Est **technique** toute erreur qu'aucune saisie ne peut provoquer : référence obligatoire `null`, valeur d'énumération non définie, chaîne d'ancêtres non chargée, donnée déjà corrompue en base — ces cas restent des exceptions .NET standard.
- Ce critère s'applique **quelle que soit la couche** qui détecte l'erreur : une règle de saisie que seule l'API peut vérifier (ex. fichier téléversé illisible comme image ou trop lourd) est signalée par la même `DomainRuleViolationException`, avec un code de `DomainRules`, jamais laissée remonter comme une exception technique de la bibliothèque qui l'a détectée.
- Un code publié n'est jamais renommé ni réaffecté à une autre règle (clé de localisation) ; leur unicité est vérifiée par un test.
- Une règle d'unicité garantie par la base (ex. libellé de genre, nom d'éditeur) ne peut pas être vérifiée par le domaine seul, qui ne voit pas les autres lignes : c'est l'API qui traduira la violation de l'index unique correspondant en erreur **métier** (avec son code de règle), jamais en erreur technique.
  - **Alternative écartée (exceptions .NET standard, `ArgumentException` / `InvalidOperationException`)** : levées aussi par le framework et par les erreurs de programmation, elles ne permettent pas de reconnaître une erreur métier.
  - **Alternative écartée (type résultat au lieu d'exceptions)** : imposerait de propager un résultat à travers chaque setter et chaque appelant pour un gain nul ici — une violation interrompt toujours l'opération en cours, et l'API la traduira en une réponse unique.
- **Réponse de l'API** : toute erreur renvoyée au frontend est une réponse **ProblemDetails** (seul le bilan de santé `/health`, interrogé par l'orchestrateur et jamais par le frontend, garde son propre format de réponse, y compris en `503`) (RFC 9457) dont le champ `type` porte l'une des **trois catégories** de `fonctionnel/index.md` § Présentation des erreurs, et aucune autre : c'est la seule information dont les clients ont besoin pour la présentation distinctive exigée. Ces trois valeurs sont des URN déclarées dans les contrats (`ProblemTypes` : `urn:bdtheque:problem:business`, `…:functional`, `…:technical`), le `type` d'un ProblemDetails étant une référence d'URI. Le code HTTP précise la nature de l'erreur au sein de sa catégorie, sans jamais en créer une nouvelle :
  - **métier** → `422 Unprocessable Content`, avec le code de règle (`ruleCode`) et, le cas échéant, les données utiles au message (ex. impact d'une suppression refusée) ;
  - **fonctionnelle** → `409 Conflict` (modification concurrente, cf. `choix-implementation/persistance.md` § Concurrence d'accès) ou `404 Not Found` (fiche supprimée entre-temps, identifiant inconnu) : dans les deux cas, la demande ne peut pas aboutir en l'état des données ;
  - **technique** → `500`, ainsi que toute erreur que le framework ou un middleware émet sans passer par une exception (corps de requête illisible ou non liable, route inconnue, méthode non admise, clé interne absente) : aucune saisie ne peut les produire, le frontend construisant les requêtes. Aucun détail interne dans la réponse (journaux uniquement).
  - **Deux points centraux, et deux seulement**, produisent ces réponses ; aucun endpoint ne construit lui-même une réponse d'erreur :
    - un gestionnaire d'exceptions unique (`IExceptionHandler`) pour les erreurs signalées par exception (métier, fonctionnelles, techniques) ;
    - le service ProblemDetails (`AddProblemDetails`) associé aux pages de code d'état (`UseStatusCodePages`) pour toute réponse d'erreur émise **sans corps** : le framework ne lève pas d'exception pour un échec de liaison de requête hors environnement de développement, il répond directement `400`, comme il répond `404`/`405` pour une route inconnue ; ces réponses reçoivent la catégorie **technique**. Une réponse d'erreur qui a déjà un corps (produite par le gestionnaire d'exceptions) n'est pas retouchée.
    - Garantie « aucune autre catégorie » : la personnalisation du service ProblemDetails (`CustomizeProblemDetails`) remplace par la catégorie **technique** tout `type` qui n'est pas l'une des trois catégories — en particulier le lien RFC que le framework attribue par défaut selon le code HTTP.
    - Depuis .NET 10, le middleware de gestion des exceptions ne journalise plus une exception que le gestionnaire déclare traitée : le gestionnaire journalise donc lui-même les erreurs techniques, seule trace de leur cause, la réponse n'en révélant rien.
- **Violations de contraintes en base** : la catégorie dépend de la **nature de l'échec**, que le code d'erreur PostgreSQL distingue, et non du seul nom de la contrainte — une même clé étrangère échoue côté référençant lors d'une création ou modification, côté référencé lors d'une suppression :
  - **index unique** (`23505`) → erreur **métier**, par une table *nom de contrainte → code de règle* (libellé de genre déjà utilisé, cible d'intention déjà visée…) ; une contrainte absente de cette table reste une erreur technique (elle révèle un contrôle manquant, pas une saisie à corriger). Les codes sont déclarés dans `DomainRules`, registre unique des codes. La table (`UniqueIndexRules`, `Bdtheque.Api`) couvre **tous** les index uniques du modèle, ce qu'un test vérifie dans les deux sens : un index unique ajouté sans sa règle ferait d'une erreur de saisie une erreur technique. Seuls en sont exclus, déclarés à part dans la même classe, les index des tables que seule l'application écrit, sans aucune saisie (compteurs d'audience, `choix-implementation/mesure-audience.md` § Mesure d'audience : mise en œuvre) : leur violation révèle une erreur de programmation ;
  - **texte plus long que sa colonne** (`22001`, *string_data_right_truncation*) → erreur **métier** (`Text.TooLong`) : l'utilisateur corrige en raccourcissant sa saisie. Les longueurs maximales ne sont déclarées que dans le schéma (configurations EF), sans copie dans le domaine à tenir alignée ; une seule traduction couvre ainsi tout champ texte de toute entité, présent ou futur ;
  - **violation d'une référence lors d'une suppression** (`23001`, *restrict_violation* : les références sont déclarées `ON DELETE RESTRICT`, § Suppression des entités : mise en œuvre, et PostgreSQL signale ce code, non `23503`, pour une suppression bloquée par une règle `RESTRICT`) → erreur **métier** : une référence est apparue entre le contrôle préalable et la suppression ; le point d'entrée de suppression la traduit en refus de suppression avec l'impact recalculé ;
  - **violation d'une référence hors d'une suppression** (`23001` sur la table des fiches désignées par les recherches enregistrées : une contribution désignée retirée du formulaire de son album ou de sa série) → erreur **métier** (`SavedSearch.DesignatedRecordRemoved`), que l'utilisateur résout en modifiant d'abord la recherche (`choix-implementation/recherche-avancee.md` § Recherches enregistrées : mise en œuvre) ; sur toute autre table, elle révèle un contrôle manquant et reste une erreur technique ;
  - **clé étrangère** (`23503`) levée par une **création ou une modification** → erreur **fonctionnelle** : la fiche référencée a été supprimée entre-temps, comme pour une fiche introuvable (`404`). C'est la traduction par défaut du gestionnaire d'exceptions. Aucune suppression ne produit ce code : toutes les clés étrangères du schéma sont en `RESTRICT` ou en `CASCADE` (vérifié par `DeleteRuleTests`), jamais en `NO ACTION`.
- **Pas de validation déclarative des DTO** (`AddValidation`, attributs `[Required]`…) : le domaine est l'**unique source** des règles de saisie. La validation native des Minimal API répondrait en `400` sans code de règle — une erreur métier y serait indiscernable d'une erreur technique — et dupliquerait chaque règle.

## Suppression des entités : mise en œuvre

- Les règles de `fonctionnel/regles-metier.md` § Suppression des entités sont appliquées par l'API **avant** la suppression : pour chaque lien de type *Référence*, l'API compte les fiches qui l'utilisent et refuse la suppression s'il en existe (erreur métier portant ces comptes). Un point d'entrée d'**impact de suppression** fournit ces comptes, ainsi que ceux des *Associations* et *Compositions* concernées, pour que le client construise le message de confirmation. Dans les deux cas, l'impact est une même structure, qui porte **tout ce que le message doit annoncer** : un nombre de fiches **par type d'entité** et par nature de lien (bloquante, association retirée, supprimée avec l'entité), ainsi que les **albums qui sortent de la collection** parce que la suppression emporte leur dernière édition possédée (`fonctionnel/regles-metier.md` § Suppression des entités) — effet qui ne supprime ni ne détache l'album, et qu'aucun compte de liens ne révèle.
- **La suppression n'emporte jamais plus que ce qui a été confirmé** : l'impact est accompagné d'une **empreinte** calculée sur l'**identité** de chaque fiche concernée (et non sur les seuls comptes, qui resteraient égaux si une association disparaissait pendant qu'une autre apparaissait). La demande de suppression transmet l'empreinte de l'impact affiché à l'utilisateur ; l'API **recalcule l'impact en entier** et son empreinte dans la transaction de suppression, **après avoir verrouillé** (`SELECT … FOR UPDATE`) la **racine de l'agrégat** de l'entité supprimée (ex. l'album d'une édition), **puis** la ligne de l'entité elle-même si elle n'est pas cette racine. Cet ordre racine → enfant est celui de **toute écriture sur un agrégat** (`choix-implementation/persistance.md` § Concurrence d'accès), qui verrouille sa racine avant de toucher à ses enfants : un ordre de verrouillage unique empêche deux transactions sur le même agrégat de s'attendre mutuellement (interblocage). Ce verrou rend recalcul et suppression atomiques sans passer la transaction en isolation sérialisable : toute écriture qui créerait un lien vers l'entité doit, pour vérifier sa clé étrangère, poser sur cette ligne un verrou `FOR KEY SHARE`, incompatible avec `FOR UPDATE` (PostgreSQL, *Explicit Locking*) — elle attend donc la fin de la suppression, puis échoue (erreur fonctionnelle : fiche supprimée entre-temps) ; toute écriture validée avant le verrou est vue par le recalcul ; et toute écriture sur l'agrégat, qui modifie sa racine (`choix-implementation/persistance.md` § Concurrence d'accès), attend de même. Si l'empreinte recalculée diffère (fiche concernée apparue, disparue ou remplacée entre-temps, depuis un autre onglet ou appareil), l'API refuse la suppression par une erreur **fonctionnelle** portant le nouvel impact, à reconfirmer. La garantie porte sur ce que la suppression **ajoute** à l'impact confirmé, jamais sur ce qu'une autre écriture en **retire** : un lien retiré par une autre transaction après le recalcul (retrait d'une association, qui ne pose aucun verrou sur l'entité supprimée) n'est pas détecté, et n'a pas à l'être — l'état final est alors un sous-ensemble de l'effet confirmé (le lien que la suppression aurait retiré a disparu de toute façon), sans rien d'inattendu pour l'utilisateur. Verrouiller aussi les lignes de jointure n'apporterait donc rien. La version de l'entité ne suffit pas : ajouter un genre à un album modifie l'album, pas le genre. Un impact devenu bloquant donne l'erreur métier de refus, comme ci-dessus.
  - **Forme dans l'API** : chaque ressource déclare ses liens (nature *Référence*, *Association* ou *Composition*, type d'entité, requête des identifiants liés), dont un mécanisme unique (`AggregateDeletion`, `Bdtheque.Api`) tire l'impact et la suppression. Les albums qui sortent de la collection y sont déclarés comme une nature de plus (*sortie de la collection*), calculée avec l'expression d'appartenance à la collection (`choix-implementation/api.md` § Organisation de l'API) : ils entrent ainsi dans l'impact et dans son empreinte. Les **recherches enregistrées qui désignent** la fiche supprimée ou l'une des fiches supprimées avec elle (ses *Compositions*) sont des *Références* de toute ressource (`fonctionnel/regles-metier.md` § Suppression des entités, ligne « Toute fiche ») : le mécanisme les ajoute lui-même à l'impact (type `SavedSearch`), sans qu'aucune ressource ait à les déclarer ni puisse les oublier (`choix-implementation/recherche-avancee.md` § Recherches enregistrées : mise en œuvre). Chaque groupe de ressource expose `GET …/{id}/deletion-impact` (impact et empreinte) et `DELETE …/{id}?version=…&fingerprint=…` (version de la fiche et empreinte de l'impact confirmé, en paramètres de requête, un `DELETE` n'ayant pas de corps). L'empreinte est un SHA-256 des identifiants liés, triés par nature, type d'entité puis identifiant. Un refus est une erreur métier de code `Deletion.BlockedByReferences`, un impact changé une erreur fonctionnelle (`409`) ; toutes deux portent l'impact courant dans l'extension `impact` du ProblemDetails.
  - **Enfant d'agrégat** (ex. une collection éditeur, `/admin/publishers/{rootId}/collections/{id}`) : sa suppression suit le même mécanisme, mais l'impact et la suppression sont adressés par la **racine** : la racine est verrouillée et sa version vérifiée (la version transmise est celle de la racine, `choix-implementation/persistance.md` § Concurrence d'accès), puis l'enfant est supprimé et la racine marquée modifiée. Lorsque sa suppression emporte plus que sa ligne (une intention portant sur une édition emporte l'édition), elle passe par l'opération de l'agrégat (`Album.RemovePurchaseIntent`), dont l'effet est celui que l'impact annonce. Un enfant qui n'appartient pas à la racine désignée est une fiche introuvable. Les formulaires d'un enfant portent donc la version de la racine, qui change à chaque écriture sur l'un de ses enfants.
  - Ce contrôle préalable est **indispensable** et non une simple commodité : sur une relation optionnelle dont les dépendants sont chargés en mémoire, EF Core met leur clé étrangère à `null` au lieu d'échouer, quel que soit le `ON DELETE` configuré (ex. supprimer une série dont les albums sont chargés les détacherait silencieusement).
- Le schéma reflète les mêmes règles : `ON DELETE RESTRICT` pour chaque *Référence*, fiches désignées par une recherche enregistrée comprises (filet de sécurité, traduit en erreur métier s'il se déclenche malgré le contrôle préalable), `ON DELETE CASCADE` pour chaque *Composition* (album → éditions, contributions, intentions ; édition → visuels, intention ; série → contributions template ; éditeur → collections) et pour les tables de jointure des *Associations* (genres, univers). Chaque clé étrangère du schéma est classée dans l'une de ces natures par `DeleteRuleTests` (`Bdtheque.Infrastructure.Tests`), qui échoue pour toute clé étrangère ajoutée sans classement : une relation laissée au comportement par défaut d'EF Core échapperait sinon aux règles de suppression.
- **Fichiers des visuels** : une cascade en base ne supprime pas les fichiers. Avant toute suppression qui emporte des visuels (visuel, édition, album), l'API relève leurs médias et ne les supprime du volume qu'**après** la validation de la transaction : un échec de la suppression laisse les fichiers intacts ; un échec de la suppression d'un fichier ne laisse qu'un fichier orphelin, sans incidence sur les données, rattrapé par la réconciliation décrite au `choix-implementation/domaine.md` § Visuels : stockage et traitement. Ce relevé appartient au mécanisme commun (`AggregateDeletion`), pour qu'aucune suppression ne l'oublie : les visuels concernés sont l'entité supprimée elle-même si c'est un visuel, sinon ceux que son impact annonce comme supprimés avec elle (*Composition* de type visuel d'édition) — les fichiers suivent exactement ce que l'utilisateur a confirmé, et toute ressource dont la suppression emporte des visuels doit donc les déclarer dans ses liens, ce qu'exige déjà l'exactitude de l'impact.
